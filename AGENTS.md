- Customer dashboard money summaries show **USD as the primary figure with the XAF value underneath** at the indicative 1 USD = 600 XAF rate. Account records stay denominated in XAF; USD is a display conversion only. Use the shared `DualMoney` component (`src/components/DualMoney.tsx`) with `primary="usd"` and the `XAF_PER_USD`/`formatUSD`/`formatXAF` helpers in `src/lib/format.ts` rather than re-declaring the rate or a local formatter.
- Crypto deposits use NOWPayments (hosted invoice + IPN). Admin-configured `nowpayments_enabled` / `nowpayments_api_key` / `nowpayments_ipn_secret` live in `app_settings`; the IPN endpoint is `/api/public/nowpayments-webhook` and settlement goes through the `settle_nowpayments_deposit` RPC. The `public_settings` view exposes only `nowpayments_enabled`. These require migration `supabase/migrations/20261002030000_add_nowpayments.sql`; without it the admin crypto fields and the deposit "Pay with crypto" option stay hidden and the settings save falls back gracefully.
- The admin settings save submits every field in a single UPDATE, so one column missing from `app_settings` makes PostgREST reject the whole statement (`PGRST204` / "schema cache") and **no** setting persists — including `referral_percent`, which then looks stuck at its default. `zendesk_widget_key` and `admin_email` were missing from the schema and are added by `supabase/migrations/20261003090000_add_zendesk_and_admin_email_settings.sql`. When a settings save appears to do nothing, diff the payload keys in `src/routes/admin.settings.tsx` against `information_schema.columns` for `app_settings`.
- Withdrawal submission calls the `create_withdrawal(_amount, _method, _account_name, _account_number)` RPC. The PIN confirmation step was removed from `src/routes/dashboard.withdraw.tsx`, but the database still had the old five-argument PIN-gated `create_withdrawal(_amount, _method, _account_name, _account_number, _pin)` from `20260829214843_...sql`, so every request failed with PGRST202 ("Could not find the function"). `20261003100000_fix_create_withdrawal_signature.sql` restores the four-argument signature and drops the stale overload. When a withdrawal fails with "Could not find the function", check that the RPC's argument list matches `src/integrations/supabase/types.ts`.
- Trading-bot status and profit figures must be derived from the customer's active investments and recorded profit transactions; never simulate activity or earnings.
- Registration creates the account server-side through `registerAccount` (`src/lib/register.functions.ts`) using the service role (`auth.admin.createUser` with `email_confirm: true`), then the client signs in with `signInWithPassword`. This keeps signup free of email verification and the project's leaked-password/strong-password policy. The connected Supabase project (ref `zrpgoantupgorrervdwj`) still has email confirmation ON; to remove the bypass, disable "Confirm email" and leaked-password protection in the Supabase dashboard and revert `src/routes/register.tsx` to `supabase.auth.signUp`.
- Third-party chat widgets load only from validated public identifiers saved by an administrator, preventing arbitrary embed code execution. `src/components/ZendeskLoader.tsx` reads `zendesk_widget_key` from the anonymous `public_settings` view; that column was missing from the view (the loader's select returned 400), so `supabase/migrations/20261004140000_add_zendesk_widget_key_to_public_settings.sql` recreates the view with `zendesk_widget_key`. When recreating `public_settings`, keep every public widget key in the select list — dropping one breaks its loader silently.

- Automatic withdrawals: the phone's MacroDroid macro polls the **production** site (`site_url`, e.g. jumbocm.vercel.app), not this preview, so server-route changes only reach the phone after they are merged and deployed; database migrations take effect immediately because the database is shared. Never run `select claim_auto_withdrawal()` to check the function: calling it claims (dispatches) a real payout. Inspect the function with `pg_get_functiondef` instead.
- To apply migrations with psql, strip the surrounding quotes and the `supa=` query parameter from `POSTGRES_URL_NON_POOLING` first, because psql rejects them with "invalid connection option".
- The MTN USSD code is `*126*9*{phone}*{amount}#` — destination number before amount (migration `20261004120000_phone_first_ussd_sms_approval.sql`); the amount-first form is rejected by the MTN menu. `claim_auto_withdrawal` only hands out the code and marks the withdrawal `dispatched`; it is closed by the phone reporting MTN's result. Primary path: after submitting the PIN the macro pauses, reads the USSD result off the screen (Read Screen Contents → global dictionary `jumbo_screen`) and POSTs `{code, text}` to `/api/public/withdraw-result`, which runs `tryConfirmWithdrawalFromSms` over `code + text` (the dialled code carries the destination number + amount; the screen text carries the success/failure keyword). Fallback: MTN's confirmation SMS forwarded to `/api/public/mm-sms` runs the same matcher. When adding the screen action by hand, the export schema is `m_classType: "ReadScreenContentsAction"` with `dictionaryKeys: {keys: []}`, `forceScreenRefresh`, `includeOverlays`, `includeWithoutText`, `isLocalVar`, `variableName` (verified against a real exportFormat 2 export). The phone still never parses JSON out of a response.
- The full MacroDroid file is produced at download time by the "Download full macro" button in `src/routes/admin.settings.tsx` (`downloadMacro`): it fetches the public `public/jumbocm-auto-withdrawal.macro.json` template and bakes `site_url`, `mm_webhook_secret` and `ussd_pin` from `get_app_settings_admin` into both the `variables` array and the action bodies (replacing `{v=jumbo_*}` tokens), so the imported macro needs no manual editing. The raw public file only carries the site URL — never commit the secret or PIN into it. Commit 353b538 accidentally replaced the whole settings page with the TanStack scaffold stub; the real page (918 lines, including this button) was restored from `77520d9`. Commit e4fbb30 reverted it to the stub a second time — if `src/routes/admin.settings.tsx` is 9 lines, restore it with `git show 8551839:src/routes/admin.settings.tsx > src/routes/admin.settings.tsx`.
- Admin-configurable withdrawal limits: `withdraw_min_amount` / `withdraw_max_amount` in `app_settings` (migration `20261004130000_add_withdraw_limits.sql`, defaults 250 / 50000000). They are exposed through `public_settings` so the withdraw page reads them without admin rights, and `request_withdrawal` enforces them server-side (replacing the hardcoded 250 minimum). The admin form lives in the "Withdrawal limits" section of `src/routes/admin.settings.tsx`; because the settings save is a single UPDATE, these keys are also in the schema-cache fallback strip list.
- Confirming an auto payout from the phone's on-screen USSD result is the primary path: the macro reads the screen after the PIN and POSTs `{code, text}` to `/api/public/withdraw-result`. That body **must** be parsed with the same newline tolerance as `/api/public/mm-sms` (`request.text().replace(/\r?\n/g, "\\n")` before `JSON.parse`) — the screen text is multi-line, so a raw `request.json()` throws and every report is rejected with 400, leaving the payout `dispatched` until the 10-minute re-queue dials it again and **pays a second time**. `confirmWithdrawalFromScreen` identifies the payout by the dialled code (`*126*9*{phone}*{amount}#` carries the exact destination + amount) and only uses the screen text to decide success vs failure; when the screen is unreadable it calls `failWithdrawal` (auto_state `failed`, still `pending`) instead of leaving it `dispatched`, so the retry loop can never double-pay. The SMS matcher (`tryConfirmWithdrawalFromSms`) keeps a **narrower** keyword set than the screen matcher so an unrelated deposit SMS can't close a payout. Each screen report is logged to `auto_withdraw_logs` with step `screen` and the raw text — read that row to see MTN's exact wording when a result is classified wrongly.
- The phone macro must NOT read the payout out of JSON. The hand-authored `JsonParseAction` never populated its dictionary on real devices, so `{lv=data[claimed]}` / `{lv=data[code]}` stayed unreplaced (MacroDroid leaves unknown dictionary magic text literal) — `claimed` was never `"true"`, the macro showed "Nothing to pay", and the withdrawal stayed `dispatched` even though the queue call had already claimed it. The macro now uses plain-text modes on `/api/public/withdraw-queue`: `?mode=check` returns `true`/`false` without claiming (`hasEligible()`), and `?mode=code` returns the ready-to-dial USSD code or `NONE` while claiming (`claimNext()`); the default (no `mode`) response is still the JSON `{claimed,...}`. Only local/global string magic text (`{lv=x}`, `{v=x}`) is used in the macro. When the phone still shows "Nothing to pay", check `auto_withdraw_logs` — an `id`/`detail` of `{lv=data[...]}` means an OLD macro is still installed; the phone must delete the previous macros and re-import the freshly downloaded file. The macro only reaches the phone after the branch is merged to `main` and Vercel redeploys, because the macro polls the production site.

## Dev environment (Base44)

- TanStack Start SSR app (Vite 8 + React 19 + Tailwind 4) using Bun as the package manager.
- The Vite dev server listens on port 5173 inside the container; compose maps host 3000 → container 5173.
- Source is bind-mounted at `/app`; `bun install --frozen-lockfile` runs on container start before `bun run dev`.
- The committed `.env` contains public Supabase credentials (URL + publishable key) — enough to boot and render pages.
- `SUPABASE_SERVICE_ROLE_KEY` is required for admin/server-side operations (deposit settlement, push, email) but not for booting.
- Remote Supabase is used for both auth and data; no local database service is needed.
- The connected Supabase project is supplied by the platform secrets (`VITE_PUBLIC_SUPABASE_URL` / `SUPABASE_URL`). The committed `.env` still carries an older project's public URL/key purely as a fallback, so `src/integrations/supabase/client.ts` prefers `VITE_PUBLIC_SUPABASE_*` — browser and server then agree on the connected project. Server-side clients already read `process.env['SUPABASE_URL']` / `SUPABASE_SERVICE_ROLE_KEY`.
- `supabase/migrations` contains re-baseline files (the 20260828085157/085242 batch and 20260829214657) that duplicate schema created by earlier migrations. They are now guarded with `IF NOT EXISTS` / `DROP ...
